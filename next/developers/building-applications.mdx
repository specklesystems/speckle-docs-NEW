This page is for people building an **application on top of Speckle data** — a dashboard, an
internal tool, a web app, a service that reacts to versions. Not a connector: you are not
publishing from a host application, you are reading what others published.

In 2026.9 a version's data is a [bundle](/next/developers/building-integrations) of parquet
files rather than an object graph, and that changes how your app gets at it. Which door you
take depends on whether you render.

## My app writes data

Publishing is the harder half. A 2026.9 version is a bundle built and uploaded through an
ingestion, and there is no published JavaScript bundle builder — `@speckle/objectsender`
writes object graphs, and .NET and Python are the only SDKs that build bundles today.

That leaves three honest options, in the order most teams should consider them:

| Option                                 | When it fits                                                                                    |
| -------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Publish from .NET or Python instead    | The writing half can move process or language                                                   |
| Implement the bundle contract yourself | You must stay in JavaScript, and can carry a parquet writer and the SGEO encoder                |
| Ask for compatibility mode             | You need time, your consumers still read object graphs, and you can move off by 1 November 2026 |

The wire sequence, the correctness rules and a build order are in [Publish a bundle from your
own code](/next/developers/building-integrations/publish). Read it before choosing the second
option: it is a real piece of work, and unlike the read path there is no worked sample.

## Why there is no drop-in object-graph loader

If your app is built on `@speckle/objectloader` or `@speckle/objectloader2`, the natural ask
is a version of those packages that reads bundles and hands you the same object graph —
`getRootObject()`, `__closure`, `getObjectIterator()`, unchanged. That is not coming, on
purpose.

Emulating that surface would mean rebuilding the object graph that 2026.9 retires: a third
implementation of the receive fidelity contract, kept in step with the .NET and Python SDKs
forever, reconstructing hashes and closures that no longer exist in the data. It would also
teach new apps a shape the platform is moving away from.

What to do instead depends on what you were using the graph for.

| What you used the object graph for | In 2026.9                                                                                   |
| ---------------------------------- | ------------------------------------------------------------------------------------------- |
| Reading properties across objects  | Read the eav tables. Objects are keyed by `applicationId`, properties by dotted path        |
| Walking hierarchy                  | Read typed relations. Grouping is `IN_COLLECTION` and the scene view, not nested `elements` |
| Getting geometry to draw           | Decode SGEO from the geometry shards, or bridge to the viewer                               |
| Object identity across versions    | `applicationId`, not a content hash                                                         |

The mechanics for all four are in [Load a bundle in your own
code](/next/developers/building-integrations/load). That page is written for any non-SDK
consumer, which includes you — it is not connector-specific.

<Warning>
  A loader that fetches `referencedObject` from the objects endpoints gets a 404 on every 2026.9
  version. Dispatch on `Version.schemaVersion` before you fetch, and keep your existing reader for
  the older shape.
</Warning>

## What stays the same

Your Speckle token, the GraphQL API for projects, models and versions, webhooks, permissions
and sharing are unchanged. So is the shape of the problem: list a version, fetch its data,
key your app's state to something stable. Only the fetch and the identity changed.
