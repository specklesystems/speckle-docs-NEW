Use this guide when you want a repeatable way to check model data quality in Speckle. Try a rule
quickly with a **Property checker** widget on a dashboard, save the rules that matter as a **Data
Validation check**, then fix failures in the authoring tool and re-run until the model meets your
standard. For BIM coordinators and modellers who define and run quality rules.

<Note>
  **Before you start:** You need a Speckle project with at least one published model version. Data
  Validation checks need a version in the data format introduced in 2026.9. See [Versions you can
  run against](/analytics/data-validation/overview#versions-you-can-run-against).
</Note>

## Choose what to validate

<Steps>
  <Step title="List your questions">
    Write down what you need to answer, such as "Do all doors have a fire rating?" or "Do level
    names follow our naming standard?". Group them by discipline or project phase.
  </Step>
  <Step title="Pick a quick check or a saved check">
    Use a **Property checker** widget to explore one rule on a dashboard. Use a Data Validation
    check for rules that must run the same way on every version, with history.
  </Step>
  <Step title="Plan where results are read">
    Decide whether people will read results on a dashboard or on the check's result page. You should
    know which rules belong in a saved check before you author it.
  </Step>
</Steps>

## Try a rule with Property checker

**When to use:** You want to test one rule quickly, or explore model health before you write a saved
check.

<Steps>
  <Step title="Open a dashboard with your model">
    Create or open a dashboard and add a **Model Viewer** widget with the model you want to check.
    See [Dashboards](/analytics/intelligence-dashboards).
  </Step>
  <Step title="Add a Property checker">
    Add **Property checker** from the **Basics** group in the widget panel.
  </Step>
  <Step title="Define the conditions">
    Select **Configure conditions**. The last condition is the check; the conditions above it narrow
    which elements are checked.
  </Step>
  <Step title="Read the result">
    The widget shows the pass rate and the count left after each step. Turn on **Color objects** to
    see passing and failing elements in the Model Viewer.
  </Step>
</Steps>

If the rule proves useful, note its property, predicate, and value. You will reuse them in a saved
check. For the dashboard-only version of this workflow, see [Run a quick validation
check](/analytics/dashboards/common-workflows#run-a-quick-validation-check).

## Save the rules as a Data Validation check

**When to use:** You want rules that run the same way every time, on one or more tracked models,
with a result history.

<Steps>
  <Step title="Open Run check">
    In the project sidebar, open **Data Validation**, then **Run check**.
  </Step>
  <Step title="Author the rules">
    Add one rule per requirement, using `WHERE` to scope the elements and `CHECK` for what must be
    true. Set each rule's severity and message.
  </Step>
  <Step title="Run preview">
    Run preview on a representative version. Tighten `WHERE` if the scope is too broad.
  </Step>
  <Step title="Save the check">
    Name the check, choose the tracked models, set the pass threshold, and choose manual or auto
    trigger. You should see the check under **Checks**.
  </Step>
</Steps>

Rules, tracked models, and trigger are fixed once you save. To change them, create a new check.
See [Checks](/analytics/data-validation/checks) for rule structure, predicates, related objects,
and calculated values.

<Tip>
  To run the check on every new version without anyone starting it, save it with the **auto**
  trigger. See [Validate incoming models
  automatically](/workflows/validate-incoming-models-automatically).
</Tip>

## Review the results

<Steps>
  <Step title="Start from the score">
    Open the check from **Checks** and read the overall score and the rules with the most failures.
  </Step>
  <Step title="Drill into a rule">
    Expand a rule to see how many elements each `WHERE` and `CHECK` step kept.
  </Step>
  <Step title="Look at failing elements">
    Select **View result** on a model card. Select failing rows in the table to focus those elements
    in the viewer and confirm they are real problems.
  </Step>
  <Step title="Refine the rules">
    Rebuild noisy rules in a new check, then compare its results with the original.
  </Step>
</Steps>

See [Viewing Results](/analytics/data-validation/viewing-results) for statuses, history, and
thresholds.

## Fix failures and re-run

<Steps>
  <Step title="Share results with model authors">
    Send the check's result page to the people who own the models, and point them to the most
    critical rules first. Export **BCF** from the result if your team tracks issues in another tool.
  </Step>
  <Step title="Fix the model in the authoring tool">
    Correct properties, naming, and assignments in Revit, Rhino, or the other source application.
  </Step>
  <Step title="Publish and check again">
    Publish a new version, then re-run the check or let its **auto** trigger run it. You should see
    previously failing elements pass.
  </Step>
</Steps>

Repeat until failure counts are acceptable for the current phase of work. Some `info` rules may
stay as known exceptions; only `error` rules drive the overall score.

## Reuse rules across projects

A saved check belongs to its project and tracked models. To apply the same standard in another
project, recreate the check there. On an empty check, **Import IDS**, **Import COBie**, and **Import
Speckle** turn an existing requirements file into rules. See [Import rules from IDS, COBie, or
Speckle](/analytics/data-validation/checks#import-rules-from-ids-cobie-or-speckle).

### Move rules from a Model Validation widget

The **Model Validation** dashboard widget is retired: you can't add it to a dashboard. Saved
dashboards that use it, and their rulesets, are kept. Move the rules into a Data Validation check:

<Steps>
  <Step title="Export the ruleset">
    On a dashboard that has the widget, open **Model validation (beta)** in the sidebar and export
    the ruleset as JSON.
  </Step>
  <Step title="Import it into a check">
    In **Run check**, select **Import Speckle** and choose the file.
  </Step>
  <Step title="Review the import">
    Read the import notes for skipped rules or conditions, then run preview before you save.
  </Step>
</Steps>

The retired widget's JSON export does not include values from [lookup
tables](/analytics/dashboards/lookup-tables), and Data Validation checks do not read those tables.
Check every imported rule that took its allowed values from one.

## Best practices

- **Start small**: Begin with a few high‑value rules and add more as teams build confidence, rather
  than starting with an exhaustive but noisy check.
- **Separate checks by intent**: Group rules into checks that share a goal, such as safety, naming,
  or documentation; this keeps results easier to interpret.
- **Treat rules as living standards**: Update rules as your standards evolve, but communicate
  changes clearly so teams understand new failures.
- **Use severity consistently**: Use `error` for requirements that must pass and `info` for helpful
  hints that should not change the score.
- **Document assumptions**: When a rule encodes an assumption (e.g. level naming or parameter
  usage), capture that assumption in the message text.

## FAQ

<AccordionGroup>
  <Accordion title="When should I use Property checker instead of a Data Validation check?">
    Use Property checker to explore one rule quickly or test an idea on a dashboard. Use a Data
    Validation check when the rule is stable, important, and should run on every version with a
    history of results.
  </Accordion>
  <Accordion title="Can one check be used across multiple projects?">
    No. A check belongs to one project. Recreate it in each project where the same standard applies,
    importing rules from a shared IDS, COBie, or Speckle file where possible.
  </Accordion>
  <Accordion title="What happens if I need to change a rule in a saved check?">
    You can't edit the rules of a saved check; only its name and description. Create a new check
    with the changed rule. Past results stay with the original check.
  </Accordion>
  <Accordion title="How do I handle exceptions without changing the rule?">
    Mark intentional exceptions with a property in the authoring tool, and exclude them in the
    rule's `WHERE` conditions. For rare exceptions, you may decide to tolerate specific failures
    instead of weakening the rule.
  </Accordion>
  <Accordion title="Can I validate several models at once?">
    Yes, on the **Enterprise** plan a check can track more than one model. See [Multi-model
    checks](/analytics/data-validation/overview#multi-model-checks).
  </Accordion>
  <Accordion title="How do I know if a rule is too strict?">
    If a rule produces many failures that are not actionable or realistic to fix, revisit its scope
    and severity. Consider splitting it into smaller rules so teams can focus on the most important
    issues.
  </Accordion>
  <Accordion title="Who should own checks in a large organisation?">
    Typically, BIM managers, information managers, or discipline leads own checks. They coordinate
    changes, review new rules, and make sure project teams understand how validation fits into their
    workflows.
  </Accordion>
</AccordionGroup>
