This page explains rule authoring in frontend-3 Data Validation.

<Info>
  In `Current`, rules are authored for **Validation Checks** and **Standards**. If you
  are using dashboard widget rulesets, see [Classic Rules and
  Rulesets](/classic/analytics/data-validation/rules-and-rulesets).
</Info>

## Rule structure

Every rule combines filters and an assertion:

| Component       | Description                                                                 |
| --------------- | --------------------------------------------------------------------------- |
| `WHERE`         | Filter scope of objects evaluated by the rule                               |
| `AND`           | Optional additional filters within the same scope                           |
| `CHECK`         | Final validation assertion                                                  |
| Property path   | Target property (`category`, `baseline.length`, `parameters.Width.value`)   |
| Predicate       | Comparison operator (**Equals**, **Exists**, **Matches pattern**, and more) |
| Value           | Reference value for the predicate                                           |
| Report severity | `ERROR`, `WARNING`, or `INFO`                                               |
| Message         | Human-facing explanation for failed outcomes                                |

<Warning>
  Keep one terminal `CHECK` per rule. If you need multiple assertions, create multiple
  rules.
</Warning>

## Checks vs standards

- Save as **Validation Check** when rule logic is attached to tracked model runs.
- Save as **Standard** when rule logic is reusable across multiple checks.
- A check can be created from a standard, then extended for project context.

## Import formats

You can import rules from:

- **IDS**: strong fit for IFC-aligned requirements exchange
- **COBie**: strong fit for asset/information delivery requirements
- **Speckle**: existing Speckle validation definitions (JSON/TSV/CSV flows)

Use standards import when migrating existing rule libraries into project-native
standards.

## Predicates and matching

Predicate labels in UI are type-aware:

- Text: **Exists**, **Equals**, **Contains**, **Matches pattern**
- Number: **Is greater than**, **Is less than**, **Is between**
- Boolean: **Is true**, **Is false**

`Matches pattern` supports wildcard and regex-style validation, depending on
input syntax.

## Best practices

- Start with narrow `WHERE` scope to avoid noisy failures.
- Keep rule message actionable so fix owners can act quickly.
- Use standards for cross-project consistency, checks for execution context.
- Review preview output before saving to avoid false positives.

## FAQ

<AccordionGroup>
  <Accordion title="Can I convert a standard into a check?">
    Yes. Create a check from a standard, then choose tracked models and trigger settings
    for execution.
  </Accordion>
  <Accordion title="Do imported rules keep their original semantics?">
    Imports are normalized into Data Validation rule structures. Review predicates and
    messages after import to confirm expected behavior.
  </Accordion>
  <Accordion title="Where should legacy terms appear?">
    Use legacy terms only in migration or technical references. User-facing docs in
    `Current` should prefer **check** and **standard**.
  </Accordion>
</AccordionGroup>
