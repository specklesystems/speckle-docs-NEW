## Using PATs

**Best for:** Single-user tools, server-side applications, scripts, and automations.

Personal Access Tokens allow users to authenticate and interact with the Speckle API on their own behalf. They're ideal for:

- Command-line tools
- Server-side applications
- Automation scripts
- Single-user integrations

PATs can be used with any Speckle SDK or API:

- **Python SDK** - See [Python SDK Authentication Guide](/developers/sdks/python/getting-started/authentication) for detailed examples
- **.NET SDK** - See [.NET SDK Authentication](/developers/sdks/dotnet/getting-started/authentication)
- **GraphQL API** - Include token in `Authorization: Bearer YOUR_TOKEN` header
- **JavaScript/TypeScript** - Use tokens in API client configuration

<Warning>
  **Never use PATs in client-side code.** They provide full access to the user's account and should
  only be used in secure, server-side environments.
</Warning>

<Warning>
  **Store tokens securely!** Treat them like passwords—never commit them to version control or share
  them publicly. Use environment variables or secret management systems in production.
</Warning>

## Getting a Personal Access Token

<Steps>
  <Step title="Sign in to Speckle">
    Go to your Speckle Server (for example, [app.speckle.systems](https://app.speckle.systems)) and
    sign in.
  </Step>
  <Step title="Open Developer settings">
    Open the workspace switcher (the workspace name at the top of the left sidebar), select your
    name, then open **Developer**. Your name is the link to User settings, not only a signed-in
    label. See [Open user settings](/workspaces/introduction#open-user-settings).
  </Step>
  <Step title="Create a token">
    Select **New token**, give it a name, select the required scopes, then copy the token.
  </Step>
</Steps>

When creating tokens or registering applications, request only the minimum necessary scopes. This principle of least privilege reduces potential security risks.

## Choose scopes

Each scope allows its own set of actions, and scopes do not imply each other. Select every scope
your code needs.

<Warning>
  A write scope no longer includes reading. A token with only `streams:write` cannot read project
  data: add `streams:read` too. Tokens created earlier with `streams:write` alone now fail on reads
  until you create a new token with both scopes.
</Warning>

| Scope              | Allows                                                                                        |
| ------------------ | --------------------------------------------------------------------------------------------- |
| `streams:read`     | Open and list projects, models and versions; load into connectors; export the data            |
| `streams:write`    | Publish and edit, comment, share, create view links, change settings, delete, create projects |
| `profile:read`     | Read your own profile, notifications and invites                                              |
| `profile:email`    | Read your own email address                                                                   |
| `users:read`       | Look up other users' profiles                                                                 |
| `workspace:read`   | Read workspaces, use AI, read usage                                                           |
| `workspace:update` | Change workspace settings, security and AI settings; review access                            |

A token never does more than its owner can. The scopes cap what the token may do; the owner's roles
decide where. See [Roles and permissions](/workspaces/roles-and-seats).

Commenting needs `streams:write`; `streams:read` alone can view comments but not post them.

### Fine-grained scopes

The scope picker in **Developer** settings lists fine-grained scopes named `area.feature.verb`,
grouped by area, such as `project.version.read` or `project.version.write`. Through the API you can
request them alongside the scopes in the table above, in the same `scopes` list. The server lists
the ones it offers in `serverInfo.scopes`.

When you request a scope from the table above, Speckle stores it as its fine-grained equivalents,
so the token's scope list shows those names. Feature wildcards such as `project.*.read` cannot be
requested.

## Using the Token

When making API requests, include the token in the `Authorization` header:

```javascript
fetch('https://app.speckle.systems/graphql', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    Authorization: `Bearer YOUR_TOKEN`
  },
  body: JSON.stringify({ query: YOUR_GRAPHQL_QUERY })
})
  .then((response) => response.json())
  .then((data) => console.log(data))
```

This request will act on behalf of the user who owns the token, with permissions defined by the selected scopes. This means if you have a token with `streams:read` scope, you can read project data but cannot modify it.
