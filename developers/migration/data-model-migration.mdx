<Warning>
  **This page is for developers building on Speckle** — SDK consumers, GraphQL/REST API users,
  Speckle Automate developers, notebook users, and anyone reading or writing Speckle object data
  directly. If you only use Speckle through desktop connectors or the web app, see [Data model
  migration for workspaces](/workspaces/data-model-migration) instead.
</Warning>

<Note>
  For a summary of everything that changed for developers in 2026.9, see [What's new for
  developers](/whats-new/developers).
</Note>

## What changed

2026.9 introduced a new underlying data model that improves scalability, storage efficiency, and performance. It replaces the tree-and-Proxy object graph of versions published before 2026.9 with two things working together: a columnar property store for fast querying and aggregation, and an explicit relational layer describing how elements relate to one another — containment, connectivity, systems, materials — richer than Proxies. See [Object model](/developers/object-model/overview).

This is a foundational change, not a cosmetic one. It's what lets Speckle handle much larger models, and the relational layer specifically is what lets newer features — including Speckle Intelligence — answer questions about how things connect and contain each other, not just look up properties on individual objects.

## What stayed the same

Your published data stays readable. Versions published before 2026.9 keep their object graph, and current connectors, SDKs, and the server still load them. Your desktop and web workflows stay the same once your connectors are up to date, and they are faster on the new format.

## Why this change

- **Scale.** The object graph became slow and memory-intensive as models grow larger. The new format is built to hold much larger models without that penalty.
- **Performance.** Faster extraction, loading, and querying — for you and for anything built on top of the data.
- **A real analytical model.** Speckle's data becomes something you can query and aggregate directly, rather than something you have to walk and reconstruct object by object.
- **AI support.** Speckle Intelligence queries both properties and relations directly, which is what lets it answer topology questions — what's connected to what, what's contained in what — rather than just looking up a single object's properties.

## Who's affected

Everyone who reads versions published by 2026.9 connectors needs up-to-date clients. A connector from 2026.8 or earlier cannot load those versions, and an SDK build from before 2026.9 gets a 404 on them. Update connectors within the upgrade window, open until **1 November 2026**; see [Upgrade window for 2026.9](/it-admin/connector-updates#upgrade-window-for-2026-9). Update SDK dependencies before your scripts read 2026.9 versions.

The next area to watch is data that reaches Speckle without a desktop connector: **ACC sync** and **file uploads**, including drag-and-drop. That data uses the new format by default. If something downstream — a custom integration, a script, an API consumer — expects the old format and breaks as a result, ask us to switch your workspace to **compatibility mode**, which keeps writing the old format while you update. Compatibility mode is open until **1 November 2026**; see [Compatibility mode](/it-admin/compatibility-mode).

<Warning>
  Compatibility mode is a bridge, not a fix. It ends for every workspace on **1 November 2026** —
  anything relying on it needs to be migrated off before then.
</Warning>

The other area to watch, separate from ACC sync and file uploads: JavaScript or
TypeScript code that loads Speckle data itself through the **open-source Viewer package**
(`@speckle/viewer`) or the **`@speckle/objectloader` / `@speckle/objectloader2`** packages. These
packages read object graphs, and there is no updated package for bundles, so a bundle version
renders nothing and the objects endpoints return 404. This doesn't affect the .NET or Python SDKs.
It isn't limited to ACC sync or file uploads either: it applies to any bundle data your app loads,
including publishes from an upgraded connector.

If this is you, add the bundle bridge from [Load a bundle in your Viewer
app](/developers/viewer/loading-bundles), or read bundles directly as described in [Load a bundle in
your own code](/developers/building-integrations/load). Compatibility mode buys time only for ACC
sync and file uploads, until **1 November 2026**. See [Speckle Viewer](/developers/viewer/introduction)
for both routes.

**Embedding the hosted web viewer in an iframe is not affected.** Once a bridge has loaded the data, the viewer's extensions and APIs (selection,
filtering, camera control, property queries) work as before. If you're unsure which side of that
line your integration is on, [ask us](https://speckle.community/help) rather than requesting
compatibility mode speculatively.

Once connectors and SDK dependencies are up to date, desktop connector users, SDK consumers,
custom analytics, and ETL carry on as normal. One exception for API consumers: GraphQL `object.children` filtering and the REST object
endpoints don't apply to bundle versions. See [Get element data from a
version](/developers/api/graphql#get-element-data-from-a-version).

Speckle Automate functions are worth calling out specifically, since what a function needs to do depends on the format of the version it's processing, not on the function's own code:

- **SDK dependency.** A function needs `specklepy[bundle]==2026.9.0b3` (Python) or `Speckle.Automate.Sdk` 2026.9.0-beta.4 or later (.NET) to read a version in the 2026.9 format. Older function builds are not guaranteed against current servers. Update them.
- **Code that reads the tree.** A 2026.9 version arrives as `Collection` and `DataObject` objects, with `id` equal to the `applicationId`. Code that filters on `speckle_type` or expects host-specific classes needs changing. See the [.NET](/developers/sdks/dotnet/migrate-to-2026-9) or [Python](/developers/sdks/python/migrate-to-2026-9) migration page.
- **Versions published before 2026.9.** They stay readable. Older connectors, including the 2026.8 Navisworks connector, still write the object graph at publish time.

Speckle may convert a version published by an older connector to the 2026.9 format on the server. That conversion is not guaranteed. Do not assume either shape. Follow this page for the format the version actually has. The durable exception is Navisworks: there is no 2026.9 desktop connector, so new desktop publishes stay on 2026.8. See [Navisworks](/connectors/navisworks).

## Self-hosted servers

<Warning>
  The open-source Speckle Server does not support 2026.9. If you run the open-source server, pin
  your connectors to 2026.8 or earlier. 2026.9 connectors do not work against it.
</Warning>

Running your own Speckle server? A self-hosted server running a release before 2026.9 keeps working as it does today, with connectors from 2026.8 or earlier. Compatibility mode and the **1 November 2026** date do not apply to it.

If you're running Speckle's open-source core, you already own your connector distribution — that's the standard for a healthy self-hosted stack, not something Speckle auto-updates for you. If your current connector and server versions work together, pin both, and keep any of your own downstream users on that same combination.

Speckle Enterprise Server deployments, including those on your own infrastructure, can move to 2026.9. See [Upgrading to 2026.9](/developers/server/upgrades/2026-9).

<Note>
  There's no fixed date yet for this data model reaching the open-source core specifically —
  consistent with Speckle's general policy of releasing new major versions to open source once
  they're proven stable, rather than on a fixed date.
</Note>

## Migration guidance

Your published data is not on a deprecation clock: versions published before 2026.9 stay readable. Older clients are different. Speckle does not guarantee that connectors from 2026.8 or earlier, or SDK builds from before 2026.9, keep working against current servers, and they cannot load versions published by 2026.9 connectors. Update them. Speckle may convert an older-connector publish to the 2026.9 format on the server; treat that as best effort, not a guarantee. ACC sync and file uploads use the new format; if that breaks something downstream, ask us to switch your workspace into compatibility mode to keep writing the old format while you update. Compatibility mode ends on **1 November 2026**.

If you maintain internal tooling that reads Speckle data more directly than the standard SDK/API surface — something that assumes the shape of the old object model rather than going through supported accessors — update it to read bundles; see [Load a bundle in your own code](/developers/building-integrations/load). On a self-hosted server, you can pin server and connectors to **2026.8**, the last release before the new model, while you update the tool. See [Self-hosted servers](#self-hosted-servers).

## What you should do

<Steps>
  <Step title="Update your connectors">
    Update within the upgrade window, open until **1 November 2026**, together with the people you
    share models with. A connector from 2026.8 or earlier cannot load a version published by a
    2026.9 connector. Navisworks has no 2026.9 connector.
  </Step>
  <Step title="Check whether ACC sync or file uploads affect you">
    If your workflow depends on ACC sync or file uploads, and something downstream consumes that
    data directly (a script, a custom Power BI query, an API integration), ask us to switch your
    workspace into compatibility mode now. Move off it before it ends on **1 November 2026**.
  </Step>
  <Step title="Update your SDK dependencies">
    Move scripts and Automate functions to a 2026.9 SDK build before they read a version published
    by a 2026.9 connector. Automate functions need `specklepy[bundle]==2026.9.0b3` or
    `Speckle.Automate.Sdk` 2026.9.0-beta.4 or later, and code that filters on `speckle_type`
    changes. Scripts and functions follow the [.NET](/developers/sdks/dotnet/migrate-to-2026-9) or
    [Python](/developers/sdks/python/migrate-to-2026-9) migration page.
  </Step>
  <Step title="Pin your self-hosted stack, if applicable">
    If you self-host, pin your current connector-and-server combination rather than updating
    further, and keep any of your own downstream users on that same combination. See [Self-hosted
    servers](#self-hosted-servers) above.
  </Step>
</Steps>

## FAQ

<AccordionGroup>
  <Accordion title="Do I need to change anything if I only use standard connectors, SDKs, or APIs?">
    Yes: update them. A connector from 2026.8 or earlier cannot load a version published by a 2026.9
    connector, and an SDK build from before 2026.9 gets a 404 on one. Your published data stays
    readable either way. GraphQL `object.children` filtering doesn't apply to bundle versions; see
    [Get element data from a version](/developers/api/graphql#get-element-data-from-a-version).
  </Accordion>
  <Accordion title="What happens to data that's already published?">
    It remains valid and readable. The migration changed how new data is handled, not what already
    exists in your projects.
  </Accordion>
  <Accordion title="Does this affect my Speckle Automate functions?">
    Yes. A function that processes a version in the 2026.9 format needs
    `specklepy[bundle]==2026.9.0b3` or `Speckle.Automate.Sdk` 2026.9.0-beta.4 or later. The received
    tree is `Collection` and `DataObject` objects with `id` equal to the `applicationId`, so code
    that filters on `speckle_type` changes. Versions published before 2026.9 stay readable. Speckle
    may convert an older-connector publish on the server; that conversion is not guaranteed. See
    [Who's affected](#whos-affected).
  </Accordion>
  <Accordion title="What if my integration doesn't fit either 'standard SDK' or 'ACC sync/file uploads'?">
    If you maintain a production integration that reads Speckle data more directly than the standard
    SDK/API surface — loading data through `@speckle/viewer`, `@speckle/objectloader`, or
    `@speckle/objectloader2`, rather than embedding the hosted viewer or reading through
    GraphQL/REST — move it to bundles, as [Migration guidance](#migration-guidance) describes, and
    reach out via [speckle.community/help](https://speckle.community/help) or your Customer Success
    Advisor so we can walk through your specific setup.
  </Accordion>
  <Accordion title="I embed @speckle/viewer and use its selection and filtering APIs. Am I affected?">
    Yes, if your app loads Speckle data into the viewer itself: the published package has no loader
    for bundles, so a bundle version renders nothing. Selection, filtering, camera control, and
    property queries work unchanged once the data is loaded. Add the bridge from [Load a bundle in
    your Viewer app](/developers/viewer/loading-bundles). Compatibility mode buys time only for ACC
    sync and file uploads, until **1 November 2026**. Embedding the hosted web viewer in an iframe
    is not affected.
  </Accordion>
</AccordionGroup>
