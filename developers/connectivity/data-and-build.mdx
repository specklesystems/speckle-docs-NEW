Applies to every architecture in this section. For the data model, see [Object model](/developers/object-model/overview). For the files a producer writes, see [Build integrations on the bundle format](/developers/building-integrations/bundles).

Before the steps below, decide **publish only** or **publish and load** for your host (receive-only is rare—mainly consumption apps like Power BI). See [Publish & load](/developers/connectivity/integration-depth) for integration depth.

## Projects, models, and versions

- **Project** — groups work for a team or deliverable
- **Model** — logical dataset (often per discipline or file)
- **Version** — immutable snapshot after a send; design send, receive, and automation around versions

[Workspaces and projects](/workspaces/projects) · API: [Project](/developers/sdks/python/api-reference/resources/project) · [Model](/developers/sdks/python/api-reference/resources/model) · [Version](/developers/sdks/python/api-reference/resources/version)

## Extraction, conversion, serialization, transport

Speckle exchanges **objects, properties, and typed relations** in a **bundle**, not opaque files:

1. **Extraction** — read native entities or files
2. **Conversion** — map to objects keyed by `applicationId`, property paths, geometry, and relations
3. **Serialization** — write the bundle with a bundle builder
4. **Transport** — authenticate, open a model ingestion, upload the bundle; the server creates the **version**

Versions published before 2026.9 use an object graph of collections and proxies instead, described in the [Data schema](/developers/data-schema/overview).

## Semantic data, geometry, and display values

- **Semantic data** — properties in the [columnar property store](/developers/object-model/overview#columnar-property-store)
- **Geometry** — SGEO blobs; see [Geometry encoding](/developers/object-model/geometry-encoding)
- **Display geometry** — what the [Viewer](/developers/viewer/introduction) renders, attached through the `DISPLAY` relation; see [Display geometry](/developers/object-model/relations#display-geometry)

Write a display mesh for every object that renders, even when you also ship a solid, so viewers and downstream tools stay aligned.

## Suggested build order

Skip steps that do not apply (for example receive-only integrations).

<Steps>
  <Step title="Authenticate">
    Use a PAT, OAuth2, or app credentials —
    [Authentication](/developers/authentication/introduction).
  </Step>
  <Step title="Publish one object">
    Create a project and model, publish a one-object bundle, and confirm a **version** in the web
    app. See [Publish a bundle](/developers/building-integrations/publish) or the [Python
    quickstart](/developers/sdks/python/getting-started/quickstart).
  </Step>
  <Step title="Map metadata">
    Settle stable properties and `applicationId` values before you scale geometry.
  </Step>
  <Step title="Convert geometry">
    Convert the primitives your consumers need — [Geometry
    encoding](/developers/object-model/geometry-encoding).
  </Step>
  <Step title="Design incremental updates">
    Define change sets (selection, delta, full resend) and version relationships for sync.
  </Step>
  <Step title="Tune performance">
    Stream rows, shard geometry, and deduplicate definitions — see the [publish
    rules](/developers/building-integrations/publish#rules-that-decide-whether-your-bundle-is-correct).
  </Step>
  <Step title="Add receive and update">
    For bidirectional flows, see [Load a bundle](/developers/building-integrations/load) and study
    the receive paths in
    [speckle-sharp-connectors](https://github.com/specklesystems/speckle-sharp-connectors).
  </Step>
  <Step title="Package for deployment">
    Plan installers, logging, and updates — [Manual
    installation](/connectors/manual-installation/introduction) for .NET connector patterns.
  </Step>
</Steps>
