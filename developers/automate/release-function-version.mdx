# Releasing a New Version

New versions of a Function are created automatically when a new GitHub release is created.

For detailed instructions on creating a new GitHub release, refer to [GitHub's documentation](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository).

## Naming convention

We recommend using the [Semantic Versioning (Semver)](https://semver.org/) naming convention to indicate the nature of changes in your release:

- **MAJOR**: Breaking changes.
- **MINOR**: Backward-compatible functionality.
- **PATCH**: Backward-compatible bug fixes.

## Deployment process

The associated GitHub action is triggered when you create a release on GitHub. This will:

1. Spin up a deployment container.
2. Extract your function's input schema and validate it.
3. Build your function code.
4. Send the validated and compiled function code to the Speckle Automate server via an API call using your credentials.
5. Automate validates the payload and reports success.

Only code that completes these build steps successfully will be sent to Automate. Once the release is processed, your function will appear in the functions list.

## Monitoring release actions

The release process triggers a [GitHub Action](https://github.com/features/actions), which can be monitored in your GitHub repository's **Actions** tab. If errors occur during the release process, they will be displayed here.

## Troubleshooting

If you encounter issues during deployment:

- Review the error logs in the **Actions** tab for details.
- Search for solutions or ask for assistance on the [Speckle Community Forum](https://speckle.community).

### Fix a build that fails to compile a dependency

If the **Actions** log shows `Failed building wheel for <package>`, followed by `Could not find the compiler specified in the environment variable CXX`, a dependency has no prebuilt package (wheel) for the Python version in your `Dockerfile`. pip then tries to compile it from source, and the `python:<version>-slim` base image has no compiler.

This happens when the base image moves to a new Python release before your dependencies support it. For example, `duckdb` 1.5.6 has no wheels for Python 3.15, so a function that depends on it fails to build on `python:3.15-slim` and builds on `python:3.13-slim`.

To fix it:

1. Find a Python version the package supports: on its PyPI page, open **Download files**. A file whose name contains `cp313` and `manylinux` supports Python 3.13 on Automate.
2. Set the `FROM python:<version>-slim` line in your `Dockerfile` to that version.
3. Set `python-version` in your release workflow to the same version, so the input schema is extracted with the same Python.

<Tip>
If Renovate opens pull requests on your repository, add a rule to `renovate.json` so it stops proposing the unsupported Python version. Remove the rule once your dependencies support it.

```json
{
  "packageRules": [
    {
      "matchDepNames": ["python"],
      "allowedVersions": "<3.15"
    }
  ]
}
```

</Tip>

## Customise the build

The default `Dockerfile` and release workflow work for most functions. You can change them when you need to:

- **Workflow:** add build steps or artefacts to the release workflow. Keep the step that generates the function's input schema (`functionInputs.json`).
- **Runtime:** add system libraries or other dependencies to the `Dockerfile`, or change its Python version. If you change the Python version, change `python-version` in the workflow to match.
