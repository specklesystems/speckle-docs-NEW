When you send data to Speckle and expect it in the **3D viewer**, the object must expose a `displayValue` property containing renderable geometry. Without it, send can succeed while the viewer shows nothing — a common first-integration mistake.

<Info>
This page covers .NET-specific usage. For the underlying schema — what `displayValue` contains and how it relates to `DataObject` — see [Data Schema Overview](/developers/data-schema/overview) and [Object Schema: displayValue](/developers/data-schema/object-schema#displayvalue).
</Info>

## Adding a Display Value

The recommended container is `DataObject` — it already has a typed `displayValue` property, plus `properties` for semantic data, so there's nothing extra to configure and it's what the rest of the Speckle ecosystem expects:

```csharp
using Speckle.Objects.Data;
using Speckle.Sdk.Models;

var wall = new DataObject
{
    name = "Wall 01",
    properties = new Dictionary<string, object?> { ["material"] = "Concrete" },
    displayValue = new List<Base> { wallMesh },
};
```

You can also add `displayValue` dynamically to a plain `Base` — this still works, and is a reasonable shortcut for a quick script or a self-contained app that doesn't need `DataObject`'s other conventions:

```csharp
using Speckle.Objects.Geometry;
using Speckle.Sdk.Models;

var wall = new Base();
wall["name"] = "Wall 01";
wall["displayValue"] = new List<Mesh> { wallMesh };
```

<Warning>
Wrapping raw geometry primitives (`Point`, `Line`, `Mesh`) directly at the root of your sent object does **not** guarantee viewer visibility if the primitive itself isn't recognized as displayable. Wrap geometry in a `DataObject` or `Base` container with an explicit `displayValue` property — this is what the [Quickstart](/developers/sdks/dotnet/getting-started/quickstart) does.
</Warning>

## Checking for a Display Value

Use `BaseExtensions` to check whether a received object is displayable, rather than manually checking both the detached and inline property names:

```csharp
using Speckle.Sdk.Models.Extensions;

if (someObject.IsDisplayableObject())
{
    var displayGeometry = someObject.TryGetDisplayValue();
    // displayGeometry is IReadOnlyList<Base>?
}
```

`TryGetDisplayValue` checks both `displayValue` and its detached form `@displayValue` automatically.

## Custom Types and Display Values

`DataObject` (shown above) already solves this — its `displayValue` property is part of the type. This section covers the case where `DataObject`'s shape doesn't fit and you define a fully custom type instead (see [Objects and Traversal](/developers/sdks/dotnet/concepts/objects-and-traversal#custom-types)). Most Speckle connectors won't recognize a custom type during conversion — but they will still render it if it has a `displayValue`:

```csharp
[SpeckleType("MyCompany.Structure")]
public class CustomStructure : Base
{
    public required double LoadCapacity { get; set; }
    public required string Material { get; set; }

    [DetachProperty]
    public required List<Mesh> displayValue { get; set; }
}
```

<Warning>
The property name must be the exact camelCase `displayValue` (matching Speckle's `DataObject` convention). A PascalCase `DisplayValue` property serializes under a different key, so `IsDisplayableObject()`/`TryGetDisplayValue()` and the viewer will not recognize it.
</Warning>

## Troubleshooting Invisible Objects

<AccordionGroup>
  <Accordion title="Sent an object but nothing shows in the viewer">
    Check that the object (or one of its `elements`) has a `displayValue` containing `Mesh`, `Line`, or `Point` geometry. Sending a bare `Point` or `Line` at the root without a container object is a common cause.
  </Accordion>
  <Accordion title="Custom type isn't converted by a connector">
    This is expected — connectors convert known types. Add a `displayValue` so the object is at least visible and generically convertible, even if its custom properties are ignored.
  </Accordion>
  <Accordion title="displayValue is present but empty in the viewer">
    Confirm the geometry inside `displayValue` was sent successfully and isn't `null` after receive — detached properties (`@displayValue`) that failed to resolve during a partial receive will appear as `null`.
  </Accordion>
</AccordionGroup>
