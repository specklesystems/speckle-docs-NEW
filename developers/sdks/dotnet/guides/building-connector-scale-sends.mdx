## Overview

`Send`/`Send2` load an entire object graph into memory before serializing it. For host applications with tens of thousands of elements (Revit, Rhino, ArchiCAD models), that memory profile doesn't scale. `SendPipeline` streams serialization to disk as NDJSON and uploads incrementally, tracked server-side by a Model Ingestion job.

<Warning>
This is an advanced, connector-scale pathway. If you're sending model data from a script or service — not a desktop host application — use `Send2` instead. See [Send and Receive Paths](/developers/sdks/dotnet/concepts/send-and-receive-paths) for the decision guide.
</Warning>

## Prerequisites

- Speckle Server version 3.0.3 or later ([`client.Server.IsWorkspaceEnabled()`](/developers/sdks/dotnet/api-reference/resources/server) doesn't gate this — check with your server admin, or call [`model.CanCreateModelIngestion`](/developers/sdks/dotnet/api-reference/resources/model#methods))
- [Authentication](/developers/sdks/dotnet/getting-started/authentication) and a [project and model](/developers/sdks/dotnet/api-reference/resources/model) already created
- Familiarity with [Send and Receive Paths](/developers/sdks/dotnet/concepts/send-and-receive-paths)

## Complete Example

```csharp
using Microsoft.Extensions.DependencyInjection;
using Speckle.Sdk.Api.GraphQL.Inputs;
using Speckle.Sdk.Pipelines.Progress;
using Speckle.Sdk.Pipelines.Send;

// 1. Create the ingestion job
var sourceData = new SourceDataInput("my-connector", "1.0.0", fileName: null, fileSizeBytes: null);
var ingestion = await client.Ingestion.Create(
    new ModelIngestionCreateInput(model.id, project.id, "Publishing model", sourceData)
);

// 2. Create and run the pipeline
using var pipeline = provider.GetRequiredService<ISendPipelineFactory>()
    .CreateInstance(ingestion, client.Account, new Progress<StreamProgressArgs>(), cancellationToken: default);

try
{
    var reference = await pipeline.Process(myLargeModelRoot);
    await pipeline.WaitForUpload();

    // 3. Tell the server the ingestion succeeded, creating a version
    var versionId = await client.Ingestion.Complete(
        new ModelIngestionSuccessInput(ingestion.id, project.id, reference.referencedId, "Published from my connector")
    );
}
catch (Exception ex)
{
    await client.Ingestion.FailWithError(ModelIngestionFailedInput.FromException(ingestion.id, project.id, ex));
    throw;
}
```

## Step-by-Step Explanation

### 1. Create the Ingestion Job

An ingestion is the server-side tracking record for this upload. It starts in a `processing` state:

```csharp
var sourceData = new SourceDataInput("my-connector", "1.0.0", fileName: null, fileSizeBytes: null);
var ingestion = await client.Ingestion.Create(
    new ModelIngestionCreateInput(model.id, project.id, "Publishing model", sourceData)
);
```

`SourceDataInput` records which application and version produced this data — useful for diagnostics on models that fail to process.

### 2. Serialize and Upload with SendPipeline

`ISendPipelineFactory.CreateInstance` builds a pipeline bound to this specific ingestion:

```csharp
using var pipeline = provider.GetRequiredService<ISendPipelineFactory>()
    .CreateInstance(ingestion, client.Account, uploadProgress, cancellationToken);

var reference = await pipeline.Process(myLargeModelRoot);
await pipeline.WaitForUpload();
```

`Process` serializes the graph to NDJSON on disk incrementally (not all in memory at once) and returns an `ObjectReference` to the root. `WaitForUpload` blocks until the background uploader has pushed every chunk to the server — call both; `Process` returning does not mean the upload finished. `SendPipeline` implements `IDisposable` — always wrap it in a `using`.

`uploadProgress` is a required `IProgress<StreamProgressArgs>` — pass `new Progress<StreamProgressArgs>()` if you don't need to report progress to a UI, matching the pattern used by `Send`/`Send2`.

### 3. Complete or Fail the Ingestion

Unlike `Send2`, `SendPipeline` does not create a version automatically — you must explicitly tell the server the upload succeeded:

```csharp
var versionId = await client.Ingestion.Complete(
    new ModelIngestionSuccessInput(ingestion.id, project.id, reference.referencedId, "Published from my connector")
);
```

If anything goes wrong, report the failure so the ingestion doesn't stay stuck in `processing`. `ModelIngestionFailedInput.FromException` builds the input from a caught exception:

```csharp
await client.Ingestion.FailWithError(ModelIngestionFailedInput.FromException(ingestion.id, project.id, ex));
```

Use `FailWithError` for unexpected/infrastructure failures, `FailWithInvalid` when the input itself was invalid (unsupported file, bad settings), and `FailWithCancel` only when the user explicitly cancelled. See [ModelIngestionResource](/developers/sdks/dotnet/api-reference/resources/ingestion) for the full state machine.

### Cooperative Cancellation

If your connector supports cancelling an in-progress send, don't cancel the pipeline unilaterally — request cancellation, then let the sending client observe and report it:

```csharp
// Caller / UI side: request cancellation
await client.Ingestion.RequestCancellation(
    new ModelIngestionCancelledInput(ingestion.id, project.id, "User cancelled")
);

// Sending client: observe the request (via subscription) and report cooperatively
await client.Ingestion.FailWithCancel(
    new ModelIngestionCancelledInput(ingestion.id, project.id, "User cancelled")
);
```

`RequestCancellation` does not stop the pipeline by itself — it's a signal the actively-sending process must poll or subscribe to and act on.

## Common Pitfalls

<AccordionGroup>
  <Accordion title="Ingestion stuck in 'processing' forever">
    Every ingestion must end in exactly one terminal call: `Complete`, `FailWithError`, `FailWithInvalid`, or `FailWithCancel`. Wrap the pipeline call in a try/catch that always reaches one of these.
  </Accordion>
  <Accordion title="Version never appears after a successful-looking send">
    `SendPipeline` doesn't create a version on its own — you must call `client.Ingestion.Complete` after `WaitForUpload` finishes.
  </Accordion>
  <Accordion title="Object IDs don't match IDs from Operations.Send">
    `SendPipeline` uses a different serializer than `Send`/`Send2`. Don't compare or reuse IDs across the two pathways — see [Send and Receive Paths](/developers/sdks/dotnet/concepts/send-and-receive-paths).
  </Accordion>
  <Accordion title="404 or unsupported errors calling client.Ingestion methods">
    The Model Ingestion API requires server version 3.0.3 or later. Confirm server compatibility before enabling this pathway in your connector.
  </Accordion>
</AccordionGroup>
