## Prerequisites

Before you can configure Speckle Enterprise Server, your organization will have already completed the following steps:

1. **License Acquisition**: Acquired a commercial license for Speckle Enterprise Server from Speckle Systems.
2. **Package Registry Token**: Obtained a package registry token from Speckle Systems to access the private Helm charts & Docker images for Enterprise features.
3. **Package Registry URL**: Received the URL for the private package registry hosting the Enterprise Helm charts and Docker images.
4. **Cluster and dependencies**: A Kubernetes cluster with Postgres, a single-node Valkey or Redis cache, blob storage (S3-compatible or Azure), an ingress controller, a certificate manager, and the `high-priority` and `low-priority` priority classes the chart schedules with. The [Kubernetes deployment guide](/developers/server/deployment/kubernetes-with-helm) walks through each of these on DigitalOcean; the same components are needed on any provider.

## New deployments

A new deployment installs the current release line directly. There is no data to migrate, so the [upgrade order](/developers/server/upgrades/introduction#upgrade-order) applies from your first upgrade onwards, not to the install.

The current line needs the following from you before the server boots or accepts uploads. Each item is covered in this guide or on the linked release page.

| Requirement                                                                                                                             | Where                                                                   |
| --------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| A valid license in the main server secret; workspaces and the licensing module are on by default                                        | [License Key](#license-key)                                             |
| The conversion runner enabled, with a labeled node pool and an exact converter image pin; without it the server accepts no file uploads | [File imports](#file-imports-conversion-runner)                         |
| Blob storage reachable from your users' browsers and connectors, with bucket CORS                                                       | [Blob storage reachable by clients](#blob-storage-reachable-by-clients) |
| Preview rendering on CPU by default; GPU rendering is an opt-in                                                                         | [Preview rendering](#preview-rendering)                                 |

The chart also ships a compatibility layer that completes publishes arriving in the pre-2026.9 data format. A new deployment does not run it: leave the `bundle_migration_token_secret` key out of the main server secret, and turn the worker deployments off in `values.yaml`.

```yaml
bundle_migration:
  enabled: false
```

Without the key the server starts, logs one warning, and accepts 2026.9-format publishes only. A publish from an older connector, an older SDK version, or the deprecated objects REST API is rejected with `LEGACY_SEND_UNSUPPORTED` (HTTP 422); the error message points the user at the [publishing migration guide](/developers/migration/publish-through-ingestions). Treat the deployment as compatible with the 2026.9 connector and SDK line only.

## Configuration Steps

### Retrieving the Helm Chart

The Enterprise Helm chart and images are published to an OCI registry. Log in to the registry host with the token Speckle issued you:

    ```bash
    helm registry login <PACKAGE_REGISTRY_HOST> --username <PACKAGE_REGISTRY_USERNAME> --password <PACKAGE_REGISTRY_TOKEN>
    ```

`<PACKAGE_REGISTRY_HOST>` is the host part of the package registry URL. To read the chart's reference `values.yaml`, pull the chart locally:

    ```bash
    helm pull oci://<PACKAGE_REGISTRY_URL>/speckle-server-chart --version 2026.9.3 --untar
    ```

Use this file, not the one in the public GitHub repository, as the reference for the values available on your chart version.

### Image Pull Secrets

The Helm Chart references Docker Images that are hosted in the same private registry as the Helm Chart.
You will need to create an Image Pull secret in Kubernetes to allow your cluster to authenticate with the registry and pull the necessary images.

1. Create a Kubernetes Secret of type dockerconfigjson:

   ```bash
   kubectl create secret docker-registry speckle-enterprise-registry \
   --docker-server=<PACKAGE_REGISTRY_URL> \
   --docker-username=<PACKAGE_REGISTRY_USERNAME> \
   --docker-password=<PACKAGE_REGISTRY_TOKEN> \
   -n <NAMESPACE> \
   --dry-run=client \
   -o yaml | kubectl apply -f -
   ```

1. Confirm the secret is deployed successfully in the same namespace as your Speckle Server deployment.

   ```bash
   kubectl get secret speckle-enterprise-registry -n <NAMESPACE>
   ```

1. Update the Helm values.yaml file to reference the image pull secret:

   ```yaml
   imagePullSecrets:
     - name: speckle-enterprise-registry
   ```

### Deploying the Helm Chart

Prepare `values.yaml` as described in the [Kubernetes deployment guide](/developers/server/deployment/kubernetes-with-helm#configure-your-deployment), add the Enterprise values from the sections below, then install the chart at an exact version:

    ```bash
    helm upgrade --install speckle-server oci://<PACKAGE_REGISTRY_URL>/speckle-server-chart \
    --version 2026.9.3 \
    --namespace <NAMESPACE> \
    -f values.yaml
    ```

The same command applies later changes to `values.yaml`, and moves to a newer chart version when you change `--version`. If you are switching an existing open-source deployment to the Enterprise chart, run it against the existing release name and namespace; the release history is kept.

With the conversion runner enabled and `helm_test_enabled` on (the default), verify the installation:

    ```bash
    helm test speckle-server --namespace <NAMESPACE>
    ```

The test runs a conversion canary that proves the whole file-import launch path, including the image pull and node pool scheduling.

### License Key

1. Obtain your Speckle Enterprise license key from Speckle.
1. Create a Kubernetes Secret to store the license key:

   ```bash
   kubectl create secret generic license \
   --from-literal=license_token=<YOUR_LICENSE_KEY> \
   -n <NAMESPACE> \
   --dry-run=client \
   -o yaml | kubectl apply -f -
   ```

1. Update the Helm values.yaml file to reference the license secret:

   ```yaml
   server:
     licenseTokenSecret:
       secretName: 'license'
       secretKey: 'license_token'
   ```

1. Confirm the Gatekeeper module, which validates the license, is enabled. It is on by default since 2026.7; set it explicitly if your values file manages every flag:

   ```yaml
   featureFlags:
     gatekeeperModuleEnabled: true
   ```

1. Upgrade your existing Helm deployment to apply the changes (see above for instructions on how to upgrade).

1. If making any further changes to the license, note that Kubernetes does not automatically restart deployments when changes are made to secrets. Restart the 'speckle-server' and 'speckle-objects' deployments to apply the changes.

   ```bash
   kubectl rollout restart deployment speckle-server -n <NAMESPACE>
   kubectl rollout restart deployment speckle-objects -n <NAMESPACE>
   ```

<Warning>
  With the default values and no license, server pods do not start. Either wire in the license as
  above, or set `featureFlags.workspacesModuleEnabled` and `featureFlags.gatekeeperModuleEnabled` to
  `false`.
</Warning>

### (Optional) Multi-regional Deployment

Multi-regional deployments allow you to provide [data residency](/workspaces/data-residency) options for your users.

#### Pre-requisites

For each region you wish to support, you will need to deploy a Postgres and Blob Storage instance in that region. Depending on your networking requirements, you may need to set up a VPN or VPC peering connection between your Kubernetes cluster and the database/storage instances.

You will need to configure postgres to handle transactions, `max_prepared_transactions` should be set to at least 100, preferably 1000. Please refer to your Postgres documentation for instructions on how to configure this setting.

#### Configuration

1. Create a json file containing the connection details for your existing 'main' region, as follows:

   ```json
   {
     "defaultProjectRegionKey": null,
     "main": {
       "blobStorage": {
         "protocol": "<s3 or azure>",
         "accessKey": "<YOUR_BLOB_STORAGE_ACCESS_KEY>",
         "bucket": "<YOUR_BLOB_STORAGE_BUCKET>",
         "createBucketIfNotExists": true,
         "endpoint": "<YOUR_BLOB_STORAGE_ENDPOINT>",
         "publicEndpoint": "<YOUR_BLOB_STORAGE_PUBLIC_ENDPOINT>",
         "s3Region": "<YOUR_BLOB_STORAGE_REGION>",
         "secretKey": "<YOUR_BLOB_STORAGE_SECRET_KEY>"
       },
       "postgres": {
         "connectionUri": "<YOUR_POSTGRES_CONNECTION_URI>",
         "databaseName": "<YOUR_DATABASE_NAME>",
         "publicTlsCertificate": "<YOUR_PUBLIC_TLS_CERTIFICATE>"
       }
     },
     "regions": {}
   }
   ```

   These details should match the connection details you provided when deploying your existing open source Speckle server instance. The `main` region is a required region.

   The `connectionUri` for Postgres should be in the following format:

   ```text
   postgresql://<DB_USER>:<DB_PASSWORD>@<DB_HOST>:<DB_PORT>/<DB_NAME>?sslmode=require
   ```

   The `null` value for the default project region key means that the `main` region will be used as the default region for new projects. This can be updated later as we add support for additional regions.

1. Update the same json file with the connection details for each additional region you wish to support. Each region should be given a unique region id. Each region is appended to the `regions` object as follows:

   ```json
   "regions": {
     "<REGION_ID>": {
       "blobStorage": {
         "accessKey": "<YOUR_BLOB_STORAGE_ACCESS_KEY>",
         "bucket": "<YOUR_BLOB_STORAGE_BUCKET>",
         "createBucketIfNotExists": true,
         "endpoint": "<YOUR_BLOB_STORAGE_ENDPOINT>",
         "s3Region": "<YOUR_BLOB_STORAGE_REGION>",
         "secretKey": "<YOUR_BLOB_STORAGE_SECRET_KEY>"
       },
       "postgres": {
         "connectionUri": "<YOUR_POSTGRES_CONNECTION_URI>",
         "databaseName": "<YOUR_DATABASE_NAME>",
         "publicTlsCertificate": "<YOUR_PUBLIC_TLS_CERTIFICATE>"
       }
     }
   }
   ```

   If you wish to set a different default region, update the `defaultProjectRegionKey` value to match the region id of the region you wish to set as default.

1. Create a Kubernetes secret to store the multi-region configuration:

   ```bash
   kubectl create secret generic multi-region-config \
   --from-file=multi-region-config.json=<PATH_TO_JSON_FILE> \
   -n <NAMESPACE> \
   --dry-run=client \
   -o yaml | kubectl apply -f -
   ```

1. Update the Helm values.yaml file to reference the multi-regional configuration secret:

   ```yaml
   multiRegion:
     config:
       secretName: 'multi-region-config'
       secretKey: 'multi-region-config.json'
   ```

1. To enable multi-regional support, update the Helm values.yaml file to include the following feature flag:

   ```yaml
   featureFlags:
     workspacesMultiRegionEnabled: true
   ```

1. Upgrade your existing Helm deployment to apply the changes (see above for instructions on how to upgrade).

1. If adding further regions, note that Kubernetes does not automatically restart deployments when changes are made to secrets. Restart the 'speckle-server' and 'speckle-objects' deployments to apply the changes.

   ```bash
   kubectl rollout restart deployment speckle-server -n <NAMESPACE>
   kubectl rollout restart deployment speckle-objects -n <NAMESPACE>
   ```

#### Giving access to regions in Speckle Server UI

The region is not yet selectable by users in the Speckle Server's UI. You first need to create the region via Speckle Server's UI.

1. Ensure you are logged in to the Speckle server with an account that has server admin privileges.
1. Navigate to Server Settings > Regions.
1. Select `Create` to add a new region.
1. Select the region id that corresponds to the region details you added in the multi-regional configuration json file.
1. Fill in the required details for the new region, including the region name. This is the name that will be displayed to users.
1. Save the new region.
1. Once the region is created, users can select it when creating a new workspace. Please refer to [the workspace guide](/workspaces/data-residency) for further details.

### File imports (conversion runner)

From 2026.9, [direct uploads](/connectors/direct-uploads/introduction) and CDE syncs convert files in your cluster: the server launches one Kubernetes Job per file from the `speckle-converters` image, on a node pool you provision. The runner is off by default, and the chart cannot responsibly turn it on for you: it needs capacity and objects only you can provide. Without the runner, the server accepts no file uploads at all, including IFC.

With the runner on, the server accepts `ifc`, `rvt`, `nwd`, `nwc`, `dwg`, `dgn`, `skp`, `3dm`, `obj`, `step` and `stp`. The list is fixed by the server; there is no per-format switch. The converter image ships with the licensed ODA SDKs built in, so the ODA-based formats (`rvt`, `nwd`, `nwc`, `dwg`, `dgn`) need no credentials from you. Converting `3dm` and `obj` additionally needs a [Rhino token you supply](#rhino-token-for-3dm-and-obj).

#### What the runner needs from you

- **A node pool** for conversion Jobs, labeled `purpose=conversion` (the value of `conversionRunner.nodePool`). Conversions are bursty, memory-hungry batch Jobs; a dedicated pool keeps them off your serving nodes. Jobs default to 4Gi base memory and may grow to the configured maximum (64Gi default ceiling) for large files; each Job has a two hour deadline by default. The [node pool contract](#node-pool-contract) below is what the pool must satisfy.
- **A namespace and RBAC** for the Jobs. The chart creates them when you set `conversionRunner.createNamespace: true` and `conversionRunner.createResources: true` (both off by default so clusters that manage these objects elsewhere do not collide). The RBAC lets the server and objects service accounts launch and watch Jobs.
- **Registry credentials in the conversion namespace.** The Job pods pull the converter image from the same private registry as the chart, but from their own namespace, so the image pull secret you created for the server does not reach them. Create the same `docker-registry` Secret in `conversionRunner.namespace` (`conversion` by default) and name it in `conversionRunner.imagePullSecrets`. The Secret itself is always operator-created.

  ```bash
  kubectl create secret docker-registry speckle-enterprise-registry \
  --docker-server=<PACKAGE_REGISTRY_URL> \
  --docker-username=<PACKAGE_REGISTRY_USERNAME> \
  --docker-password=<PACKAGE_REGISTRY_TOKEN> \
  -n conversion \
  --dry-run=client \
  -o yaml | kubectl apply -f -
  ```

- **The exact converter image pin**: `conversionRunner.converterImage: ghcr.io/specklesystems/speckle-converters:2026.9.0` (or your mirrored path). Run the same `YYYY.M` converter and server line and upgrade both together: they must reference the same bundle format version. Never run the runner on a mutable `latest` tag, which silently breaks that pairing on the next push.

#### Node pool contract

Conversion Jobs are placed by the node selector `purpose: <nodePool>` and nothing else. Hand this contract to whoever provisions the pool.

- **Label and taint.** The `purpose` label is mandatory. A taint is optional and must use the `PreferNoSchedule` effect: Jobs carry no tolerations, so a hard taint strands every Job in `Pending`.
- **Three chart values must match the pool.** The chart does not validate any of them.
  - The pool's `purpose` label equals `conversionRunner.nodePool`.
  - The namespace the Jobs run in equals `conversionRunner.namespace` (`conversion` by default). The pull Secret lives there too.
  - `conversionRunner.maxMemoryMib` stays under node allocatable memory. The 64Gi default ceiling pairs with 128 GB nodes; raise it only on larger nodes.
- **Machine shape.** Memory-optimized nodes with at least 8 GB of RAM per core. The reference shape is 16 vCPU / 128 GB, which is what Speckle's hosted service runs. Give each node at least 200 GB of disk: Jobs declare no ephemeral-storage request, so nothing stops a large source file from filling a small node disk.
- **Autoscaling.** Minimum node count of at least 1, so the first upload does not wait on a scale-up and the autoscaler can see the label. Maximum roughly the number of large conversions you expect to run at once, plus 2.

<Note>
  Provider-specific: on GKE and AKS, set the label and the `PreferNoSchedule` taint on the node pool
  itself (`--node-labels` / `--node-taints` on GKE, `--labels` / `--node-taints` on AKS) so new
  nodes inherit them. On EKS, set them on the managed node group or the Karpenter NodePool. A label
  added by hand to running nodes is lost when the autoscaler replaces them.
</Note>

<Note>
  If your ingress load balancer targets every node in the cluster, also label the pool
  `node.kubernetes.io/exclude-from-external-load-balancers=true`. Autoscaler churn on the conversion
  pool otherwise adds and removes load balancer members on every scale event.
</Note>

<Warning>
  A `NoSchedule` or `NoExecute` taint on the pool leaves every Job, including the `helm test`
  canary, stuck in `Pending`. If you taint the pool, use `PreferNoSchedule`.
</Warning>

#### Enable the runner

<Steps>
  <Step title="Enable the runner on the server">
    Set `featureFlags.jobRunnerEnabled: true` in your values. Upload acceptance derives from the
    runner: once the server restarts with it on, the web app's upload dialog lists the supported
    formats.
  </Step>
  <Step title="Configure the conversionRunner block">
    Set the exact converter image, the node pool, the creation gates, and the pull Secret. Your
    values should end up matching the excerpt below.
  </Step>
  <Step title="Deploy and verify">
    Install or upgrade the release as described above. With `helm_test_enabled` on, `helm test` runs
    a conversion canary that proves the whole launch path, including the image pull and node pool
    scheduling. Then upload a file through the web app: it should convert and open in the viewer.
  </Step>
</Steps>

A complete values excerpt, with Jobs pinned to a pool labeled `purpose=conversion` and the chart creating the namespace and RBAC:

```yaml
featureFlags:
  jobRunnerEnabled: true

conversionRunner:
  converterImage: ghcr.io/specklesystems/speckle-converters:2026.9.0
  createNamespace: true
  createResources: true
  nodePool: 'conversion'
  imagePullSecrets:
    - speckle-enterprise-registry
```

<Warning>
  With `accIntegrationEnabled` set and the runner off, the server refuses to start ("Syncs require
  the conversion jobrunner"). Enable the runner before you turn on any CDE integration.
</Warning>

<AccordionGroup>
  <Accordion title="Conversion Jobs, or the helm test canary, sit in Pending. Why?">
    The Jobs cannot find a node. Run `kubectl describe pod` on one and look for `FailedScheduling`:
    either no node carries the `purpose` label matching `conversionRunner.nodePool`, or the pool has
    a `NoSchedule` taint, which Jobs carry no toleration for. Fix the label or change the taint
    effect to `PreferNoSchedule`; the Jobs schedule on their own once a node qualifies.
  </Accordion>
  <Accordion title="A conversion Job is stuck in ImagePullBackOff. What is missing?">
    The pull Secret in the conversion namespace. Create it there with the command above and name it
    in `conversionRunner.imagePullSecrets`; the server namespace's Secret does not reach the Jobs.
  </Accordion>
  <Accordion title="File uploads are rejected as unsupported before anything uploads. What did I miss?">
    The runner is off. With `featureFlags.jobRunnerEnabled` false the server accepts no file
    formats, and the web app says "Unsupported file type" as soon as a file is picked.
  </Accordion>
</AccordionGroup>

#### Rhino token for 3dm and obj

`3dm` and `obj` convert through the runner's Rhino leg, which runs Rhino under McNeel's core-hour billing. The token is yours to supply, not Speckle's: generate a core-hour billing auth token in the [McNeel Licenses Portal](https://www.rhino3d.com/licenses) under your own Rhino account or team, so that usage bills to your organization.

Leave `conversionRunner.rhinoToken` empty if you do not need those formats. To enable them, store the token in a Kubernetes Secret and name it in `conversionRunner.rhinoToken`:

```bash
kubectl create secret generic rhino-token \
--from-literal=rhino_token=<YOUR_RHINO_TOKEN> \
-n <NAMESPACE> \
--dry-run=client \
-o yaml | kubectl apply -f -
```

```yaml
conversionRunner:
  rhinoToken:
    secretName: 'rhino-token'
    secretKey: 'rhino_token'
```

The token reaches each Rhino-routed Job as a plain environment variable, readable by anyone with pod read access in the conversion namespace; the chart's Role grants that only to the server and objects service accounts.

<Warning>
  The server accepts `3dm` and `obj` uploads whether or not a Rhino token is configured. Without
  one, those uploads fail fast with a configuration error instead of launching a Job.
</Warning>

### Blob storage reachable by clients

Model data moves between clients and object storage over pre-signed URLs, in both directions: publishing clients (connectors, the conversion Jobs, SDK scripts) upload directly to the bucket, and the viewer running in the user's browser fetches directly from it. The object storage endpoint embedded in those URLs must therefore be addressable by your users' machines and browsers, not just from inside the cluster. Check the following:

1. **Endpoint reachability.** Pre-signed URLs are generated against `s3.publicEndpoint` when set, otherwise `s3.endpoint`. If your storage is reached through a private or in-cluster address, set `s3.publicEndpoint` to an HTTPS URL your clients can reach, and keep `s3.endpoint` on the private address for server-side traffic. Browsers must also trust the certificate on that public endpoint.
2. **Bucket CORS (S3-compatible storage only).** Browsers call the pre-signed URLs cross-origin. The bucket must allow `GET`, `PUT`, and `POST` from your users' origins, and allow all request headers. Expose at least the `ETag`, `Content-Encoding`, and `Content-Length` response headers. `ETag` is required: the upload flow reports it back to the server to complete a publish. Azure Blob Storage needs no manual setup; the server configures the service's CORS rules at startup.

To verify, publish a model from a connector and open it in the viewer from a machine outside your network. If the publish stalls after the file is prepared, or the viewer shows an empty scene while the browser console logs blocked or failing storage requests, revisit the two points above.

### Preview rendering

The preview service renders on the CPU by default (via SwiftShader), so it works on clusters without GPUs. CPU rendering is markedly slower than a GPU and may struggle on very large models; give the preview pods 1 to 3 CPUs and 2 to 4Gi memory.

To render previews on a GPU instead:

- Use passthrough NVIDIA GPUs only (never vGPU), driver 515.48.07 or newer, with `nvidia-drm modeset=1`.
- Set `preview_service.webgpu.requireHardwareAdapter: true` and reserve the GPU via the preview pod resources. With the flag on, a pod that cannot see a hardware adapter fails readiness loudly instead of silently falling back to slow CPU rendering.

### (Optional) Microsoft Azure Blob Storage support

In addition to S3 compatible blob storage supported by the open source Speckle server, the Enterprise licensed Speckle server supports also supports Azure Blob Storage.

To use Azure Blob Storage with Speckle Enterprise Server, you will need to update your Helm values.yaml file to include the necessary configuration details for your Azure Blob Storage account. This includes setting the provider to 'azure' and providing the endpoint URL, bucket name, and access key for your Azure Blob Storage account.

```yaml
# for legacy backwards-compatibility reasons, the blob storage configuration is still nested under an 's3' key, but the provider can be set to 'azure' to use Azure Blob Storage instead of S3 compatible storage
s3:
  protocol: 'azure' # defaults to 's3', which is the only option for open source deployments, and can be set to 'azure' to use Azure Blob Storage
  endpoint: https://<YOUR_AZURE_STORAGE_ACCOUNT_NAME>.blob.core.windows.net # required when provider is set to 'azure', this should be the endpoint URL for your Azure Blob Storage account and must be reachable by the Speckle server.
  publicEndpoint: https://<YOUR_AZURE_FRONT_DOOR_HOSTNAME> # optional, if not provided will default to the same value as endpoint. This must be a domain that is reachable by both your end users and the Speckle server. When configuring Azure Front Door in front of your Azure Blob Storage, the origin header must not be rewritten and must match the publicEndpoint hostname.
  bucket: <YOUR_AZURE_BLOB_CONTAINER_NAME> # required when provider is set to 'azure', this should be the name of the blob container you wish to use for Speckle
```

### Upgrade notes

Upgrades between release lines from 2026.7 onwards are documented in the [self-hosted upgrade guide](/developers/server/upgrades/introduction), one page per release. Read the guide before every upgrade: releases must be applied in order, and 2026.9 has no downgrade path.

#### Upgrading to 3.0.21

- If you have enabled the Ingress, you will first need to delete all Ingress resources in your namespace before upgrading to version 3.0.21. This is because we have changed the Ingress controller in a way which does not allow for in-place patching during the upgrade process.
