2026.7 is the first rung of the [upgrade ladder](/developers/server/upgrades/introduction).
It flips eight Helm chart defaults on, starts a background data migration
that must fully drain before you upgrade to 2026.8, and removes frontend-2.
Read the [license requirement](#before-you-upgrade-the-license-requirement)
before running the upgrade: a default upgrade without a license fails at
startup. Also check the
[infrastructure requirements](#infrastructure-requirements): from this
release, clients upload and download model data through pre-signed URLs, so
your object storage must be reachable from outside the cluster.

## Before you upgrade: the license requirement

Eight chart defaults flip on in 2026.7 (full list in the next section). Two
of them, **workspaces** and **gatekeeper**, require a valid Speckle
Enterprise license at startup:

- With `featureFlags.gatekeeperModuleEnabled: true` (the new default), every
  server pod mounts a `LICENSE_TOKEN` environment variable from the
  `license_token` key of your main server secret (or from
  `server.licenseTokenSecret` if you override it). If that key does not
  exist, pods fail with `CreateContainerConfigError` and never start.
- If the key exists but the token is invalid, module initialization throws
  and the server exits during startup.

Pick one of these before upgrading:

**Option A: wire in your license.** Add your license token under the
`license_token` key of the main server secret, or point the chart at
wherever you keep it:

```yaml
server:
  licenseTokenSecret:
    secretName: '' # defaults to the main server secret (secretName)
    secretKey: '' # defaults to license_token
```

**Option B: keep the modules off.** If you do not have a license, disable
both modules explicitly in your values file:

```yaml
featureFlags:
  workspacesModuleEnabled: false
  gatekeeperModuleEnabled: false
```

<Warning>
  Upgrading to 2026.7 with unmodified default values and no license fails at startup. This is not a
  degraded mode; the server does not come up. Contact Speckle if you need a license.
</Warning>

The following values default to enabled in the 2026.7 `speckle-server`

| Value                                      | What it enables                                                  |
| ------------------------------------------ | ---------------------------------------------------------------- |
| `featureFlags.workspacesModuleEnabled`     | Workspaces (requires a license, see above)                       |
| `featureFlags.gatekeeperModuleEnabled`     | Gatekeeper, the licensing module (requires a license, see above) |
| `featureFlags.savedViewsEnabled`           | Saved views                                                      |
| `featureFlags.issuesModuleEnabled`         | Issues                                                           |
| `featureFlags.multipleEmailsModuleEnabled` | Multiple email addresses per account                             |
| `featureFlags.retryErroredPreviewsEnabled` | Periodic retry of errored previews                               |

## Infrastructure requirements

Each release page lists the infrastructure a deployment must provide for
that release to function. For 2026.7 there is one requirement.

### Object storage must be reachable by clients

2026.7's data module moves packfile traffic out of the server and onto
pre-signed URLs, in both directions:

- **Publish**: the server hands publishing clients (connectors, the import
  workers, SDK scripts) a pre-signed `PUT` URL, and the client uploads the
  packfile directly to object storage.
- **View**: the artifact endpoints return pre-signed `GET` URLs per file,
  and the viewer running in the user's browser fetches the packfiles
  directly from object storage.

Both mean the object storage endpoint embedded in those URLs must be
addressable by your users' machines and browsers, not just from inside the
cluster. Check the following:

1. **Endpoint reachability.** Pre-signed URLs are generated against
   `s3.publicEndpoint` when set, otherwise `s3.endpoint`. If your storage
   is reached through a private or in-cluster address (for example
   in-cluster MinIO), set `s3.publicEndpoint` to an HTTPS URL your clients
   can reach, and keep `s3.endpoint` on the private address for
   server-side traffic. Browsers must also trust the certificate on that
   public endpoint.
2. **Bucket CORS (S3-compatible storage only).** Browsers call the
   pre-signed URLs cross-origin, so the bucket must allow `GET`, `PUT`,
   and `POST` from your users' origins, allow all request headers, and
   expose at least the `ETag`, `Content-Encoding`, and `Content-Length`
   response headers. `ETag` is required: the upload flow reports it back
   to the server to complete a publish. Azure Blob Storage needs no manual
   setup; the server configures the service's CORS rules at startup.

To verify, publish a model from a connector and open it in the viewer from
a machine outside your network. If the publish stalls after the file is
prepared, or the viewer shows an empty scene while the browser console
logs blocked or failing storage requests, revisit the two points above.

## The objects migration runs by default

This is the operational centerpiece of 2026.7. With
`featureFlags.dataModuleEnabled: true`, the server backfills every existing
version from per-object rows in the Postgres `objects` table into
DuckDB-based packfiles in your blob storage. New versions are packed as
they are created; the backfill converts your history.

The backfill is additive: it writes packfiles and index rows and stamps
each version as migrated. It does not delete or modify rows in the
`objects` table.

<Warning>
  The migration must fully drain before you upgrade to 2026.8. The 2026.8 bundle migration builds on
  the packfiles this backfill produces. Use the monitoring queries below to confirm completion.
</Warning>

### Load profile

- The backfill runs inside your existing server pods. Every server pod
  participates by default; set `IS_OBJECT_PROCESSOR=false` on a deployment
  to opt specific pods out (for example a pod pool dedicated to GraphQL
  traffic).
- A scheduler scans for unmigrated versions once per minute and enqueues up
  to 35 of them when the queue is quiet. It backs off automatically while
  more than 4 jobs are in flight, so the backfill trickles rather than
  bursts.
- Each pod processes one migration job at a time by default
  (`DATA_PROCESSING_CONCURRENCY`, default `1`). A single job can hold
  multiple gigabytes of memory for large models, and concurrency multiplies
  that peak. Raise it only if your pods have memory headroom; memory
  exhaustion is the main way this worker gets OOMKilled.
- Expect, until the backfill drains: sustained read load on Postgres (the
  `objects` table), extra CPU and memory use on server pods, temporary
  DuckDB and NDJSON files on pod-local disk, and write traffic to blob
  storage.
- Failed versions are retried up to 3 times; the last error is recorded per
  version.

### Monitoring the migration

<Warning>
  There is no Prometheus metric for this migration. The only monitoring surface is SQL against the
  server's Postgres database.
</Warning>

Versions still waiting to be migrated (a version is migrated once its
`commits.objectKey` is set):

```sql
SELECT count(*) AS remaining
FROM commits
WHERE "objectKey" IS NULL;
```

Overall progress:

```sql
SELECT
  count(*) FILTER (WHERE "objectKey" IS NOT NULL) AS migrated,
  count(*) AS total
FROM commits;
```

Versions that have exhausted their retries, grouped by error:

```sql
SELECT vm.error, count(*) AS versions
FROM versions_migration vm
WHERE vm.migrated = false
  AND vm.retries >= 3
GROUP BY vm.error
ORDER BY versions DESC;
```

The migration is complete when `remaining` is `0` and the failure query
returns no rows. If versions keep exhausting their retries, contact Speckle
support with the output of the failure query.

<Note>
  Multi-regional deployments: run these queries against each regional database. The scheduler
  processes all registered regions.
</Note>

## IFC importing works out of the box

With `ifc_import_service.enabled: true` (the new default), the chart
deploys the IFC import worker and drag-and-drop IFC uploads work with no
further configuration. The worker uses the main server database for job
delivery by default; no dedicated queue database is required.

To opt out, set `ifc_import_service.enabled: false`. This is also the lever
if you do not want the worker's resource footprint (it requests 100m CPU
and 512Mi memory, with limits of 1 CPU and 2Gi).

### Breaking change: dedicated file-import queue database wiring

This affects a narrow set of deployments. Before 2026.7, the chart
implicitly referenced a `fileimport_queue_postgres_url` secret key for the
import queue. That implicit wiring is removed chart-wide.

You are affected if either:

- you configured `ifc_import_service.db.connectionString` with only a
  `secretName` and no `secretKey`, or
- you relied on the implicit `fileimport_queue_postgres_url` key to point
  the import queue at a dedicated database.

If so, set the key explicitly:

```yaml
ifc_import_service:
  db:
    connectionString:
      secretName: your-secret-name
      secretKey: fileimport_queue_postgres_url
```

<Warning>
  Without the explicit `secretKey`, the import queue silently repoints to the main server database.
  Nothing errors; imports keep working, but against the main database instead of your dedicated one.
</Warning>

<Note>
  `featureFlags.nextGenFileImporterEnabled` no longer plays any part in this wiring; the value is
  inert. Dedicated queue-database wiring is driven purely by
  `ifc_import_service.db.connectionString`.
</Note>

## frontend-2 is removed

The 2026.7 chart no longer contains frontend-2: its deployment, values, and
image publishing are all gone. frontend-3 is the only web frontend. If your
values file still carries a `frontend_2` block, it is now ignored; remove
it during this upgrade.

## Object-upload rate limits relaxed

The default rate limits for `POST /objects/:streamId` are raised so large
imports no longer hit `429` responses:

| Limit                                                      | Old default | New default |
| ---------------------------------------------------------- | ----------- | ----------- |
| `RATELIMIT_POST_OBJECTS_STREAMID` (per second)             | 6           | 30          |
| `RATELIMIT_BURST_POST_OBJECTS_STREAMID` (burst per minute) | 400         | 3000        |

Explicitly set environment variable values still take precedence over the
new defaults.

## FAQ

<AccordionGroup>
  <Accordion title="Can I skip 2026.7 and go straight to 2026.8?">
    No. Upgrades walk the [ladder](/developers/server/upgrades/introduction) in order, and the
    objects migration that 2026.7 runs must drain before 2026.8's bundle migration can complete.
  </Accordion>
  <Accordion title="Does the objects migration change or delete my existing data?">
    No. It writes packfiles to blob storage and index rows to Postgres, and stamps each version as
    migrated. Rows in the `objects` table are left untouched.
  </Accordion>
  <Accordion title="How long will the migration take?">
    It depends on version count and model size. The scheduler enqueues at most 35 versions per
    minute and each pod works one job at a time by default, so large histories drain over days
    rather than hours. Track the `remaining` count with the monitoring query above.
  </Accordion>
  <Accordion title="I upgraded without a license and my pods will not start. What now?">
    That is the expected failure mode: `CreateContainerConfigError` on the missing `license_token`
    key, or a startup throw on an invalid token. Either wire in a valid license or set
    `featureFlags.workspacesModuleEnabled: false` and `featureFlags.gatekeeperModuleEnabled: false`,
    then upgrade again.
  </Accordion>
</AccordionGroup>
