This guide is for IT administrators who need to prepare Databricks and connect a SQL warehouse in Speckle before users can register tables and query them in AI chat and data tools.

<Note>
  The Databricks integration is in **Beta** and is enabled per workspace. If you don't see
  Databricks under your project's **Integrations**, submit the [beta access request
  form](https://share-eu1.hsforms.com/2Jy0rZrUfQpKkbvtomaxXMA2fs1ws).
</Note>

If your organisation has not prepared Databricks for Speckle yet, an IT administrator (or anyone with Databricks admin access) must complete the steps below.

Speckle acts in Databricks through a **service principal** you create (OAuth machine-to-machine). The SQL grants you assign to that service principal in Databricks define exactly what Speckle can read and change. Grant only the catalogs, schemas, and tables you want to expose.

## Prepare the service principal and grants

<Steps>
  <Step title="Create a service principal">
    In your Databricks account console, go to **User management \> Service principals** and add a new service principal for Speckle.

    <Frame>
      <img src="/images/connectors/data-warehouses/databricks_create_service_principal.png" alt="Create a service principal in Databricks" />
    </Frame>

    You should see the new service principal in **User management \> Service principals**.

  </Step>
  <Step title="Generate an OAuth secret">
    On the service principal, open **Secrets** and generate a new **OAuth secret**.

    <Frame>
      <img src="/images/connectors/data-warehouses/databricks_create_secret.png" alt="Generate an OAuth secret for the service principal" />
    </Frame>

    A new OAuth secret is listed and ready to copy.

  </Step>
  <Step title="Copy the Client ID and secret">
    Copy the **Client ID** (the service principal's Application ID) and the **Client secret**. The secret is shown only once at creation — copy it now and store it securely.

    <Frame>
      <img src="/images/connectors/data-warehouses/databricks_clientid_secret.png" alt="Client ID and secret for the service principal" />
    </Frame>

    You now have the Client ID and secret ready to paste into Speckle.

  </Step>
  <Step title="Get your SQL warehouse connection details">
    Use a **serverless** SQL warehouse: it starts in seconds and stops on its own when idle. Open **SQL Warehouses \> your warehouse \> Connection details** and note the **Server hostname** (your *Workspace host*) and the **HTTP path**.

    <Frame>
      <img src="/images/connectors/data-warehouses/databricks_warehouse_configs.png" alt="SQL warehouse connection details: server hostname and HTTP path" />
    </Frame>

    You now have the server hostname and HTTP path needed to connect.

  </Step>
  <Step title="Grant access to the data you want to expose">
    Grant the service principal `USE CATALOG`, `USE SCHEMA`, and `SELECT` on the specific catalogs, schemas, and tables users need — plus access to the SQL warehouse. `SELECT` on a table requires `USE CATALOG` on its catalog and `USE SCHEMA` on its schema, so grant all three. To expose every table in a schema at once, grant `SELECT` on the schema instead of listing each table.

    Run the grants below in a Databricks SQL editor or notebook. The grantee is the service principal's **Client ID** (its Application ID, from the earlier step).

    The service principal can now read only the catalogs, schemas, and tables you granted.

  </Step>
</Steps>

```sql title="Grant read access to the Speckle service principal"
-- Replace the catalog/schema/table names and the Client ID with your own.
GRANT USE CATALOG ON CATALOG `speckle`                       TO `9918081b-778e-469a-a69b-acc950b08e09`;
GRANT USE SCHEMA  ON SCHEMA  `speckle`.`cost`                TO `9918081b-778e-469a-a69b-acc950b08e09`;
GRANT SELECT      ON TABLE   `speckle`.`cost`.`diamonds`     TO `9918081b-778e-469a-a69b-acc950b08e09`;
GRANT SELECT      ON TABLE   `speckle`.`cost`.`walls`        TO `9918081b-778e-469a-a69b-acc950b08e09`;
```

## Connect the warehouse in Speckle

<Steps>
  <Step title="Open the Databricks integration">
    In Speckle, open your project's **Integrations \> Databricks** and select **Connect to Databricks**.

    The connection form opens.

  </Step>
  <Step title="Enter your warehouse details">
    Fill in:
    - **Workspace host** — e.g. `dbc-xxxxxxxx.cloud.databricks.com` (hostname only, no `https://`).
    - **SQL warehouse HTTP path** — e.g. `/sql/1.0/warehouses/abcd1234efgh5678`.
    - **Authentication method** — **OAuth (service principal)** with your **Client ID** and **Client secret**, or **Personal access token** with your token.

    <Frame>
      <img src="/images/connectors/data-warehouses/connect_databricks.png" alt="Connect Databricks connection form" />
    </Frame>

    Your warehouse connection details are ready to test.

  </Step>
  <Step title="Test the connection">
    Select **Test connection**. Speckle runs a `SELECT 1` round-trip against your warehouse. If the test times out on a stopped warehouse, try again once it's running.

    You should see a success message with the response time, or an error explaining what failed.

  </Step>
  <Step title="Save">
    Select **Connect** (or **Save changes**). The connection is now stored for your workspace and you can browse it.
  </Step>
</Steps>

<Note>
  If you don't use a serverless SQL warehouse, expect longer start times. Pro and classic warehouses
  can take several minutes to start after they stop, and Speckle waits about two minutes, so a test
  or table refresh on a stopped warehouse can time out.
</Note>

After this is enabled, users can continue with [Databricks user setup](/connectors/cloud-integrations/databricks).

## What Speckle can do in Databricks

**Speckle reads by default.** Browsing catalogs, schemas, and tables reads Unity Catalog and doesn't start the SQL warehouse. Speckle runs `SELECT` queries to test the connection, preview tables, and build snapshots. On managed and external Delta tables, each snapshot refresh first runs `DESCRIBE HISTORY ... LIMIT 1` and then reads the table at that version (`VERSION AS OF`). If `DESCRIBE HISTORY` fails, the refresh reads the latest data without a version. With the Databricks tools in AI chat, a workspace admin can also have the chat read live rows and update tables, each time after they allow it.

**Databricks SQL grants define the boundary.** Speckle can only read the catalogs, schemas, and tables you granted to the service principal, and can only update tables you granted a write privilege on.

**With the Databricks tools on, Databricks data in Speckle is for workspace admins.** Only workspace admins can query Databricks data sources. A chat that holds Databricks data can be shared only after its owner confirms, and public report links don't load Databricks data sources. See [Share a chat that holds Databricks data](/connectors/cloud-integrations/databricks#share-a-chat-that-holds-databricks-data).

**Connection secrets are protected in Speckle.** They are encrypted in your browser before they are sent, stored encrypted at rest, and never shown again after you save the connection.

## Let AI chat update tables

If your Speckle deployment turns on the Databricks tools in AI chat, workspace admins can ask the chat to update values in an existing table, for example to write quantities from a model into a cost table. The chat can write to a table only if the service principal has a write privilege on it, and only after the person who asked reviews every statement on the card and allows the write. A workspace admin can also run the same write through the Speckle API, which shows no card but needs the same grant. To keep Speckle read-only, grant only the read privileges above.

To let the chat update a table, grant `MODIFY` on it in addition to the read grants above:

```sql title="Let the Speckle service principal update one table"
GRANT MODIFY ON TABLE `speckle`.`cost`.`walls` TO `9918081b-778e-469a-a69b-acc950b08e09`;
```

`MODIFY` covers the update and the new columns. Databricks' `MODIFY` also allows inserts and deletes, which Speckle never runs. Without a write privilege, Databricks rejects the write and the table stays unchanged. The chat can write only to managed or external Delta tables.

A write runs these statements in order:

1. `SELECT` reads the rows whose key columns match. If a key matches more than one row, the write stops here.
2. `ALTER TABLE ... ADD COLUMNS` adds new nullable columns. It runs only when the write adds a column, and the card lists it before anything runs. Speckle can't remove a column after it adds one.
3. `MERGE INTO ... WHEN MATCHED ... THEN UPDATE` updates the rows whose key columns match. It never inserts or deletes rows, and it skips keys that match no row.
4. `SELECT` reads the same rows back to verify the update.
5. `DESCRIBE HISTORY ... LIMIT 1` reads the table's latest version, which Speckle records as the version after the write.

<Tip>
  If users never need new columns, Databricks' `UPDATE` privilege is enough for the update itself,
  on compute that supports [fine-grained DML
  privileges](https://docs.databricks.com/aws/en/data-governance/unity-catalog/access-control/fine-grained-dml-privileges)
  (Beta). Adding a column still needs `MODIFY`.
</Tip>

On a self-hosted Speckle Enterprise Server, your server admin turns the tools on. See [Databricks tools in the assistant](/developers/server/deployment/enterprise-license#databricks-tools-in-the-assistant).
