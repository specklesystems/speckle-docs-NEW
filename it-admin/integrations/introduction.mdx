This page explains what is common to every Speckle cloud integration before you enable a specific one. It is written for administrators who govern access on the source side — an Autodesk hub, a ProjectWise datasource, a Databricks or Snowflake account — and need to know what Speckle will and will not be able to reach.

## The rule that applies everywhere

**Speckle never has more access than you grant on your side.** There is no Speckle-side switch that widens what an integration can read. Every integration authenticates with an identity you control, and the permissions attached to that identity in your platform are the whole boundary.

Two consequences follow:

- **You govern in your own tools.** Access reviews, revocation, and scoping happen in Autodesk admin, ProjectWise, Unity Catalog, or Snowflake roles — the places your team already audits. Speckle adds nothing that needs a parallel policy.
- **Nothing is crawled.** Speckle does not index your hub, datasource, catalog, or lake. It reads only the specific files or tables a user selects, only when a sync or query runs, and only if the identity is permitted to read them.

## Two kinds of integration

|                          | Syncs                                                                                                      | Subscriptions                                                                                                |
| ------------------------ | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **Source**               | BIM and CAD files in a CDE — Autodesk Forma Data Management (ACC), Bentley ProjectWise                     | Tables and views in a data platform — Databricks, Snowflake                                                  |
| **What Speckle does**    | Reads the file, converts it into Speckle objects, and stores the result in the Speckle project             | Registers the table and runs read-only `SELECT` queries against it on demand                                 |
| **Where the data lives** | A converted copy lives in Speckle; the source file is untouched                                            | Data stays in your platform; Speckle stores the query results it needs to render a view or answer a question |
| **Direction**            | Read only. Speckle never writes files back to the CDE; [ACC issue sync](#acc-issue-sync) writes ACC issues | Read only. Speckle never writes, alters, or deletes                                                          |

### Syncs (BIM and CAD)

A sync takes a file the user can already open in the CDE and converts it into Speckle's object model — atomised into individual elements with their properties, normalised so a Revit wall and an IFC wall can be queried the same way. That conversion is what enables the viewer, dashboards, AI chat, and the SQL join to your tables. The source file is read, not modified, and the sync does not trigger paid translation or consume cloud credits on the CDE side.

### Subscriptions (data)

A subscription points at a table or view in your warehouse. Speckle presents a browser of what the service identity can see; a user picks a table, and Speckle queries it read-only when a dashboard, AI chat, or SQL join needs it — for example, joining a cost table to the elements of a synced model. Queries run on your warehouse compute under the service identity, so they appear in your query history and consume your compute like any other client.

## Sync guarantees

This section applies to every sync integration — Autodesk Forma Data Management (ACC), Bentley ProjectWise, Trimble Connect, and any integration added later. It states what Speckle guarantees when a sync runs and what it does when a sync does not.

### Terms

- **Source platform** — the system Speckle reads from. It is the system of record for its own files and version history; Speckle never is.
- **Sync** — a standing link between one file in the source platform and one Speckle model. Created once, it produces Speckle versions over time. Pausing or disconnecting a sync stops new versions; existing versions stay.
- **Source version** — one saved state of a file in the source platform. The source platform numbers and retains these.
- **Change detection** — how Speckle learns a new source version exists. ACC notifies Speckle at publish time. ProjectWise and Trimble Connect are checked on a schedule, so Speckle sees only the source version current at check time; versions superseded between checks are never seen.
- **Sync attempt** — one run of a sync against one source version Speckle has seen: download, convert, store. Each seen source version gets exactly one attempt, which either succeeds (a Speckle version now exists) or fails (it does not).
- **Speckle version** — the converted copy a successful attempt stores. Speckle versions are ordered by their creation date, not by source version number. A version from an automatic sync is dated when Speckle created it; a version from a historical import is dated when the source version was created in the source platform.
- **Latest version** — the most recently created Speckle version of a model, and what the viewer, dashboards, and API show by default.
- **Retry** — running a new sync attempt against the same source version as the sync's most recent attempt. Available from the sync's status in the UI, and only while that source version is still the newest one Speckle has seen. Once a newer source version has been seen, the earlier one can no longer be retried.
- **Missed source version** — a source version whose attempt failed and that can no longer be retried because a newer source version has since been seen, or that Speckle never saw because the integration was disconnected, its authorisation had lapsed, or the sync was paused. Both cases are handled the same way.
- **Re-publish** — producing a new source version in the source platform (re-issuing, re-saving, or re-uploading the file). Speckle treats it as any other new source version.
- **Historical import** — a user choosing earlier source versions from the source platform's version history and syncing them into the model, up to five at a time. Available for ACC syncs. Each imported Speckle version is dated when that source version was created, so it takes its place in the past and never becomes the latest version.

### The guarantee

**Syncs are forward-only.** A sync acts only on the source version current when it runs, and each new Speckle version comes from a source version at least as new as the one before it. A model's latest version always reflects the most recent _successful_ sync attempt. It is never an older source version brought in out of order.

**A user can import earlier versions where the integration supports it.** A historical import is an explicit user action, not something Speckle does on its own. The imported Speckle version is dated when the source version was created, so it slots into the model's history behind newer versions and the latest version is unchanged. Currently ACC only; see [Import earlier versions](/connectors/cloud-integrations/acc#import-earlier-versions).

**A failed attempt can be retried only while its source version is still the newest.** If the most recent attempt failed, retry it from the sync's status. The retry runs against the same source version, so it cannot disturb version order. Once a newer source version has been seen, the earlier failure is a missed source version and the retry is no longer offered.

**Missed source versions are not replayed by Speckle.** Whatever the cause — a Speckle-side fault, or the source platform's availability, authorisation, permissions, or rate limits — Speckle does not retry a missed source version later or backfill it on its own. The next successful attempt produces the next Speckle version. To get a missed version into Speckle, import it from the file's version history where the integration supports it, or re-publish it on the source platform.

**What Speckle does when attempts fail.** Speckle surfaces the failure in the sync's status, fixes the cause so subsequent attempts succeed, and confirms with the reporting customer. Where the cause was on Speckle's side, Speckle notifies affected workspace admins with the models involved, the date window, and how to recover the missed versions. How a failure is surfaced — auto-pause, email to the sync's creator — is described on each integration's page.

**Responsibility boundary.** Every integration is a two-party arrangement. Speckle is not responsible for source versions that fail to sync because of the source platform's availability, authorisation, permissions, rate limits, or content Speckle cannot process. Speckle's service commitments cover Speckle's half.

**Disconnection gaps.** If an integration is disconnected, a sync is paused, or authorisation lapses, source versions during the gap are missed. Reconnecting or resuming continues from the next source version Speckle sees, not from the gap.

<Note>
  The source platform keeps its full version history regardless of what Speckle synced. Treat
  Speckle's version list as the record of what was successfully converted, not as a mirror of the
  source platform's history.
</Note>

## Who the integration acts as

This is where the integrations differ, and it determines where you scope access.

| Integration                              | Identity Speckle uses                                                                  | What a user can reach                                                                                              |
| ---------------------------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Autodesk Forma Data Management (ACC)** | The signed-in user's own Autodesk account, via OAuth with read-only scopes             | Exactly the hubs, projects, and folders that user already has in Autodesk — no more, no less                       |
| **Bentley ProjectWise**                  | A Speckle service account you add to projects, plus the user's own Bentley credentials | Only projects the service account has been added to **and** the user is permitted to see                           |
| **Databricks**                           | A service principal you create, with SQL grants you assign                             | Whatever the service principal has `SELECT` on — the same for every user in the Speckle workspace                  |
| **Snowflake**                            | A service user you create, with a role you grant                                       | Whatever the role can read — the same for every user in the Speckle workspace                                      |
| **ACC issue sync**                       | One Autodesk account a workspace admin connects for the workspace, with `data:write`   | Issues in the ACC projects where that account has Manage issues — the same for every user in the Speckle workspace |

**For ACC, permissions are per user and follow the user.** If Sarah is a member of two hubs — full read on one, a single project on the other — she can sync anything she can read across both, and nothing else. Change her Autodesk permissions and her Speckle reach changes with them. There is nothing for you to enable beyond registering the Speckle integration on the hub once.

**For Databricks and Snowflake, permissions are per workspace and follow the service identity.** Everyone in the Speckle workspace sees the same set of tables: the ones you granted. This is deliberate — it lets you publish a curated, governed surface (specific schemas, views with row filtering applied on your side) without mirroring individual user entitlements into Speckle. If different teams need different data, use separate Speckle workspaces with separate service identities.

**ProjectWise is both.** The service account must be added to a project for it to be reachable at all, and within that the user's own ProjectWise permissions still apply.

### ACC issue sync

[ACC issue sync](/connectors/cloud-integrations/acc-issue-sync) is the one place Speckle writes to a source platform, and it writes issues, never files. It does not use each user's sign-in. A workspace admin connects one Autodesk account, and Speckle reads and writes ACC issues for every project in the workspace as that account. Speckle's issue permissions decide who can send an issue to ACC or change its status there, and every write appears in ACC as the connected user, with the Speckle person named in the text. Scope it by giving that account Manage issues only in the ACC projects you want synced. See [Connect an account for issue sync](/it-admin/integrations/acc#connect-an-account-for-issue-sync).

Issue sync is not forward-only like file syncs: after an outage or a pause, it brings every linked issue to its current state in ACC.

<Note>
  Speckle's own project roles govern what happens *after* data is in Speckle — who can view,
  comment, or load a model. They do not extend anyone's reach into the source platform.
</Note>

## What Speckle never does

- **Write back files.** No integration modifies, uploads, or deletes files in the source platform. Scopes and grants for syncing are read-only by design; in ACC, the requested scopes are `account:read`, `user-profile:read`, `data:read`, `data:search`, `bucket:read`, `viewables:read`, and `openid`. The one write is [ACC issue sync](#acc-issue-sync): its connected account also has `data:write`, and Speckle uses it only to create and update ACC issues and add comments to them. It never deletes an ACC issue.
- **Crawl or enumerate beyond the identity's permissions.** Speckle lists only what the identity can list, and only when a user opens the browser view.
- **Escalate.** Speckle cannot request broader access on a user's behalf; broadening access is always an action you take in your own admin console.
- **Expose credentials.** Service principal secrets and private keys are encrypted in the browser before they are sent, stored encrypted at rest, and never displayed again after you save them.

## Recommended scoping patterns

For **ACC**, if you want tighter control than per-user inheritance, create a dedicated Autodesk account with access to only the projects you want synced and have users sign in to Speckle with it.

For **Databricks and Snowflake**, treat the service identity as a publishing surface. Grant it access to a dedicated schema or set of views rather than to raw tables, and apply any row- or column-level policies on your side — Speckle only ever sees what the query returns.

For **ProjectWise**, add the service account only to the projects that need syncing; unlisted projects are invisible regardless of user permissions.

## FAQ

<AccordionGroup>
  <Accordion title="Can a Speckle user see something in our hub they can't see in Autodesk?">
    Files, no. ACC access for syncing is the user's own Autodesk permission set, requested
    read-only. If they cannot open a file in Autodesk, they cannot sync it. Issues are the
    exception: with [ACC issue sync](#acc-issue-sync) on, the issues pinned to a synced file appear
    to everyone who can view the Speckle project, whatever their ACC role.
  </Accordion>
  <Accordion title="If I revoke a user's access on our side, does Speckle keep the data?">
    New syncs and queries stop immediately. Data already converted into a Speckle project stays
    there, governed by Speckle project roles, until a project owner removes it — the same as any
    file a user had legitimately exported while they had access.
  </Accordion>
  <Accordion title="Why does everyone in the workspace see the same Databricks tables?">
    Because the integration authenticates as the service principal, not as each user. Scope the
    service principal to a governed set of views; use separate workspaces if teams need different
    surfaces.
  </Accordion>
  <Accordion title="Do syncs or queries cost us anything on our platform?">
    Syncs read existing files and derivatives and do not trigger paid translation. Warehouse queries
    run on your compute under the service identity and are billed by your platform like any other
    client.
  </Accordion>
  <Accordion title="A source version was missed. Can Speckle recover it?">
    Not on its own: syncs are forward-only and Speckle does not replay missed source versions,
    whatever the cause. If it is the sync's most recent attempt, retry it from the sync's status.
    Otherwise, on ACC, a user with access to the sync's settings can [import
    it](/connectors/cloud-integrations/acc#import-earlier-versions) from the file's version history;
    on other integrations, re-publish the file on the source platform and Speckle syncs it as a new
    version. See [Sync guarantees](#sync-guarantees).
  </Accordion>
  <Accordion title="Will the latest version in Speckle ever be older than the latest in our CDE?">
    It can lag — by the check interval on scheduled integrations, plus conversion time — and it can
    be missing a version that failed to sync. It will never be an older version brought in after a
    newer one: the latest Speckle version always comes from the most recent successful sync, and
    earlier versions a user imports are dated at their source creation time, so they never displace
    it.
  </Accordion>
  <Accordion title="Does Speckle store our warehouse data?">
    Speckle stores the query results it needs to render a dashboard or answer a question, not a copy
    of the table. The table of record stays in your warehouse.
  </Accordion>
</AccordionGroup>
